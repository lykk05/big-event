## P0 安全与正确性（4 项）

### P0-1 文章接口存在越权（IDOR）

**位置**：`mapper/ArticleMapper.java` 第 21、25、29 行；`service/impl/ArticleServiceImpl.java`。

**现状**：`list` 在 SQL 里带了 `and create_user = #{id}`，所以列表只能看自己的文章；但 `update`、`findById`、`delete` 三条语句只按主键操作，没有任何归属条件：

```java
@Update("update article set title=#{title},... where id=#{id}")
void update(Article article);

@Select("select * from article where id=#{id}")
Article findById(Integer id);

@Update("delete from article where id= #{id}")   // 删除用 @Update 不合适
void delete(Integer id);
```

**风险**：任意登录用户把 id 改成别人的文章 id，就能读、能改、能删。这是最典型的 IDOR，也是安全评审必问的一条。`ArticleServiceImpl.update` 里还有一句 `article.setCreateUser(id)`，但它没有被 SQL 写入，纯属无效赋值，容易让人误以为做了归属校验。

**改法**：SQL 条件 + Service 校验双保险。

```java
@Update("update article set title=#{title}, content=#{content}, cover_img=#{coverImg}, " +
        "state=#{state}, category_id=#{categoryId}, update_time=#{updateTime} " +
        "where id=#{id} and create_user=#{createUser}")
void update(Article article);

@Select("select * from article where id=#{id} and create_user=#{createUser}")
Article findOwnedById(@Param("id") Integer id, @Param("createUser") Integer createUser);

@Delete("delete from article where id=#{id} and create_user=#{createUser}")
void delete(@Param("id") Integer id, @Param("createUser") Integer createUser);
```

Service 里先判存在、再判归属，给出明确错误，而不是静默失败：

```java
@Override
public void update(Article article) {
    Map<String, Object> map = ThreadLocalUtil.get();
    Integer uid = (Integer) map.get("id");

    Article db = articleMapper.findById(article.getId());
    if (db == null) throw new BizException("文章不存在");
    if (!db.getCreateUser().equals(uid)) throw new BizException(403, "无权操作该文章");

    article.setCreateUser(uid);
    article.setUpdateTime(LocalDateTime.now());
    articleMapper.update(article);
}
```

> `BizException` 目前不存在，需要按 P1-9 先补上；在补上之前可暂用 `RuntimeException`。

**验收**：用 A 用户的 token 拿 B 用户的文章 id 调 `PUT /article` 与 `DELETE /article`，均应返回 403 或"无权操作"，且数据未变。

### P0-2 JWT 载荷里塞了口令散列

**位置**：`controller/UserController.java` 第 92-96 行。

**现状**：

```java
Map<String, Object> claims = new HashMap<>();
claims.put("id", loginUser.getId());
claims.put("username", loginUser.getUsername());
claims.put("password", loginUser.getPassword());   // 把散列值写进了令牌
String token = JwtUtil.genToken(claims);
```

**风险**：JWT 只是 base64url 编码加签名，签名保证"没被篡改"，不保证"看不见"。任何人拿到 token，解开中间那段就能读到口令散列，接下来就是离线爆破。等于把 P0-4 的 MD5 问题放大了一个数量级。`@JsonIgnore` 只影响 JSON 序列化，管不到 JWT 的 claims。

**改法**：载荷只放标识，不放任何凭据。

```java
Map<String, Object> claims = new HashMap<>();
claims.put("id", loginUser.getId());
claims.put("username", loginUser.getUsername());
String token = JwtUtil.genToken(claims);
```

顺带处理一个连带问题：`updatePwd` 修改口令后，老 token 里如果还留着旧散列，语义就错了；现在只放 id 与 username，这个隐患自然消失。

**验收**：把 token 中间段 base64 解码，只应看到 `id`、`username`、`exp`，不应出现 `password`。

### P0-3 用户资料更新接口存在越权（2026-11-16 新增）

**位置**：`controller/UserController.java` 第 119-123 行；`service/impl/UserServiceImpl.java` 第 36-40 行；`mapper/UserMapper.java` 第 21-22 行；`pojo/User.java` 第 17-18 行。

**现状**：`update` 直接接收整个 `User`：

```java
@PutMapping("/update")
public Result update(@RequestBody @Validated User user){
    userService.update(user);
    return Result.success();
}
```

`UserServiceImpl.update` 不覆盖 id，SQL 用的是请求体里的 id：

```java
@Update("update user set nickname = #{nickname}, email = #{email}, " +
        "update_time = #{updateTime} where id = #{id}")
void update(User user);
```

而 `User.id` 上还有 `@NotNull`，等于强制客户端提交 id。任何登录用户把 id 改成别人的用户 id，就能修改对方的昵称和邮箱。

**风险**：与 P0-1 同属 IDOR，但入口在用户表上，更隐蔽；昵称被改成违规内容、邮箱被改成攻击者的地址，都会留下后续风险（尤其是以后加"邮箱找回密码"时）。这也是一次典型的 mass assignment：客户端能写的字段超出了接口本意。

**改法**：入参收窄为 DTO，当前用户 id 只从登录上下文取，请求体里的 id 一律不采信。

```java
@Data
public class UserUpdateDTO {
    @NotEmpty(message = "昵称不能为空")
    @Pattern(regexp = "^\\S{1,10}$", message = "昵称长度为1-10位，不能包含空格")
    private String nickname;

    @NotEmpty(message = "邮箱不能为空")
    @Email
    private String email;
}
```

```java
@PutMapping("/update")
public Result update(@RequestBody @Validated UserUpdateDTO dto) {
    userService.updateCurrentUser(dto);
    return Result.success();
}
```

```java
@Override
public void updateCurrentUser(UserUpdateDTO dto) {
    Integer uid = (Integer) ThreadLocalUtil.get().get("id");
    User user = new User();
    user.setId(uid);                 // id 只来自登录上下文
    user.setNickname(dto.getNickname());
    user.setEmail(dto.getEmail());
    user.setUpdateTime(LocalDateTime.now());
    userMapper.update(user);
}
```

补充两点：

- 实体不再作为更新入参后，`User.id` 上的 `@NotNull` 可以移除；它本来只是为了满足入参校验。
- 前端 `UserInfo.vue` 仍会提交 id，Spring Boot 默认忽略未知字段（`FAIL_ON_UNKNOWN_PROPERTIES=false`），前端可以不改。

**验收**：A 用户提交 B 的 id 与自己的昵称/邮箱，B 的资料不变；A 自己的资料正常更新。

### P0-4 口令用无盐 MD5 存储

**位置**：`utils/Md5Util.java`；`controller/UserController.java` 第 89、148 行；`service/impl/UserServiceImpl.java` 第 31、53 行。

**现状**：注册时 `Md5Util.getMD5String(password)`，登录时再算一次比对。MD5 无盐、无迭代、算力极便宜，一张普通显卡每秒能撞上亿次。

**风险**：库一旦泄漏（SQL 注入、备份文件、误传仓库），口令基本等于明文。这是安全扫描的必报项，也是面试里"你们口令怎么存的"最常见的追问点。

**改法**：引入 BCrypt，只加 `spring-security-crypto` 一个依赖，不引入整个 Security starter，避免默认过滤链把现有接口全拦了。

```xml
<dependency>
  <groupId>org.springframework.security</groupId>
  <artifactId>spring-security-crypto</artifactId>
</dependency>
```

迁移时有三个坑必须一起处理，否则代码跑不通：

0. **先加宽 `user.password` 字段**。当前是 `varchar(32)`（按 MD5 长度设计），BCrypt 散列固定 60 字符，直接注册会报 `Data truncation: Data too long for column 'password'`：

```sql
alter table `user` modify column password varchar(100);
```

1. **不能调用现有的 `userService.updatePwd(...)` 做静默 rehash**：`UserServiceImpl.updatePwd` 内部还会再做一次 MD5（第 53 行），结果是 `MD5(BCrypt(...))`，下次登录两种格式都匹配不上。
2. **登录流程里 `ThreadLocal` 是空的**：`/user/login` 在拦截器白名单里，`updatePwd` 却从 `ThreadLocalUtil.get()` 取 id（第 51-52 行），会直接 NPE。

所以新增一个显式接收 id 与已编码口令的方法：

```java
// UserService
void updatePwdHash(Integer userId, String encodedPassword);

// UserServiceImpl
@Override
public void updatePwdHash(Integer userId, String encodedPassword) {
    userMapper.updatePwd(encodedPassword, userId);   // 复用现有 SQL，但不再做 MD5
}
```

登录处按存储格式分支，兼容存量 MD5 数据并在登录成功后升级：

```java
private final PasswordEncoder encoder = new BCryptPasswordEncoder();

String stored = loginUser.getPassword();
boolean matched;
if (stored.startsWith("$2a$") || stored.startsWith("$2b$") || stored.startsWith("$2y$")) {
    matched = encoder.matches(rawPassword, stored);
} else {
    // 存量无盐 MD5
    matched = Md5Util.getMD5String(rawPassword).equals(stored);
    if (matched) {
        userService.updatePwdHash(loginUser.getId(), encoder.encode(rawPassword));
    }
}
if (!matched) {
    return Result.error("密码错误");
}
```

同时把注册（`UserServiceImpl.register`）与改密接口（`UserController.updatePassword`）里的 MD5 一并换成 `encoder.encode(...)`；改密时校验旧口令也要按上面的分支处理。存量 MD5 数据会在用户下一次登录时自动升级，不需要一次性刷库。

**验收**：`password` 字段长度 ≥ 60；新注册用户库里是 `$2a$` 开头的串；老用户登录一次后库里变成 BCrypt；登录功能不回退。

### P0-5 分类接口存在越权（2026-11-16 新增）

**位置**：`controller/CategoryController.java`；`service/impl/CategoryServiceImpl.java`；`mapper/CategoryMapper.java` 第 21-30 行。

**现状**：`list` 带 `create_user` 条件，但 `findById`、`update`、`delete` 都只按主键操作，和 P0-1 是同一类问题：

```java
@Select("select * from category where id = #{id}")
```

## P1 架构与可维护性（12 项）

### P1-1 登录业务滞留在 Controller

**位置**：`controller/UserController.java` 的 `login`（80-104 行）与 `updatePassword`（133-163 行）。

**现状**：`login` 一个方法里干三件事——比对口令、签发令牌、写 Redis 白名单；`updatePassword` 里比对旧口令、判两次输入一致、调 Service、删 Redis。规则写在表现层，`UserServiceImpl` 只负责查人。

**风险**：同一规则无法被第二个入口复用（比如以后加手机号登录、加管理端登录，就要复制一遍）；Controller 单测要连带 Redis 与 JWT，几乎测不了。

**改法**：下沉到 `LoginService`，Controller 退回为参数接收与响应包装。

```java
public interface LoginService {
    String login(String username, String rawPassword);   // 返回 token
    void logout(String token);
    void changePassword(String username, String oldPwd, String newPwd, String token);
}
```

新口令的格式校验也放在这里统一做（见 P2-12）。

**验收**：`UserController` 里不再出现 `Md5Util`、`JwtUtil`、`stringRedisTemplate` 三个符号；`LoginService` 能被单测覆盖（mock Redis 与 JwtUtil）。

### P1-2 实体同时是表映射、入参、出参

**位置**：`pojo/Article.java`、`pojo/User.java` 被 `@RequestBody`、`Result<T>`、MyBatis 三处共用。

**现状**：`Article` 一边被 `ArticleMapper` 映射，一边是 `ArticleController` 的 `@RequestBody`，一边又是分页结果的元素类型。`User` 同理，还被 `updateAvatar`、`updatePwd` 直接操作。

需要说明的是：**口令泄漏这一点已经由 `@JsonIgnore` 挡住了**（`User.java:22`），所以这条不是安全漏洞，而是契约问题。

**风险**：表结构一改，接口契约跟着变，前端被迫同步改；`@JsonIgnore` 这类字段级补丁也意味着"哪些字段能进出"散落在实体注解里，而不是由接口自己声明。P0-3 的越权正是"入参实体字段过宽"的直接后果。

**改法**：`ArticleDO`（持久化）/ `ArticleDTO`（入参）/ `ArticleVO`（出参）三件套，`Article` 保留为 DO；转换用 MapStruct 或一个 30 行的 Assembler 手写映射。`User` 拆出 `UserUpdateDTO`（昵称、邮箱）与 `UserProfileVO`（id、username、nickname、email、userPic，不含 password）。

**验收**：`Controller` 里不再出现裸的 `Article`、`User` 作为入参或出参类型；新增或删除一个库字段时，前端接口契约不受影响。

### P1-3 AI 模块有三处按 action 重复分派

**位置**：`service/impl/AiServiceImpl.java` 第 84-99 行 `buildSystemPrompt`、101-138 行 `buildUserContent`、178-216 行 `parseResponse`。

**现状**：三个方法各写一个 `switch (action)`，同一个动作在这三处各出现一次。七种动作 = 21 个分支点。

**风险**：新增一种动作要改三处，漏一处就是"提示词对了但解析错了"这种很难查的 bug；`switch` 里的字符串提示词还和解析逻辑分居两个方法，无法一眼看出"这个动作进出长什么样"。

**改法**：动作即策略，一个实现类承载一个动作的完整契约。

```java
public interface AiActionHandler {
    AiAction action();
    String systemPrompt(AiRequest req);
    String userContent(AiRequest req);
    AiOutputVO parse(String rawResponse) throws Exception;
}
```

```java
@Service
public class AiServiceImpl implements AiService {
    private final Map<AiAction, AiActionHandler> handlers;

    public AiServiceImpl(List<AiActionHandler> handlers) {   // 构造器注入
        this.handlers = handlers.stream()
                .collect(Collectors.toMap(AiActionHandler::action, h -> h));
    }
    // generate 里只剩：校验 → handler.systemPrompt → handler.userContent → 调用 → handler.parse → 组装
}
```

**验收**：`AiServiceImpl` 里不再有 `switch (action)`；新增第八种动作只新增一个类，不改动任何已有代码；七种动作的提示词与解析都能在同一个文件里读完。

### P1-4 每次 AI 调用都新建 RestTemplate，且用双花括号初始化

**位置**：`service/impl/AiServiceImpl.java` 第 140-176 行。

**现状**：

```java
private RestTemplate createRestTemplateWithTimeout() {
    RestTemplate restTemplate = new RestTemplate();
    restTemplate.setRequestFactory(new SimpleClientHttpRequestFactory() {{
        setConnectTimeout(connectTimeout);
        setReadTimeout(readTimeout);
    }});
    return restTemplate;
}
```

每调一次模型就 `new` 一个 `RestTemplate` 和一个请求工厂，用完即弃：连接无法复用（每次都要重新 TLS 握手，30 秒的读超时下尤其明显），`SimpleClientHttpRequestFactory` 本身也不带连接池；双花括号写法还会生成匿名内部类，IDE 与静态扫描都会提示。

**改法**：抽成单例 Bean。这个项目不需要额外依赖，JDK 自带的 `HttpClient` 内部维护连接池，配合 Spring 6.1+ 的 `JdkClientHttpRequestFactory` 即可（Boot 3.4.6 满足）：

```java
@Configuration
public class AiHttpConfig {

    @Bean
    public RestTemplate aiRestTemplate(
            @Value("${ai.api.connect-timeout:10000}") int connectTimeout,
            @Value("${ai.api.read-timeout:30000}") int readTimeout) {
        HttpClient httpClient = HttpClient.newBuilder()
                .connectTimeout(Duration.ofMillis(connectTimeout))
                .build();
        JdkClientHttpRequestFactory factory = new JdkClientHttpRequestFactory(httpClient);
        factory.setReadTimeout(Duration.ofMillis(readTimeout));
        return new RestTemplate(factory);
    }
}
```

`AiServiceImpl` 构造器注入这个 Bean，删掉 `createRestTemplateWithTimeout()`。

> 修正原文的一处说法：Spring Boot 3.4 的 `spring-boot-starter-web` **默认不包含** `httpclient5`。如果更倾向 Apache 连接池，需要显式添加 `org.apache.httpcomponents.client5:httpclient5`（版本由 Boot 管理），再使用 `HttpComponentsClientHttpRequestFactory`。

**验收**：连续调 10 次 AI 接口，服务端到 api.deepseek.com 的连接数稳定在个位；`AiServiceImpl` 不再 `new RestTemplate()`。

### P1-5 AI 异常处理丢了原因、超时靠字符串匹配

**位置**：`service/impl/AiServiceImpl.java` 第 55-63 行；第 218-234 行。

**现状**：

```java
} catch (ResourceAccessException e) {
    if (e.getMessage() != null && e.getMessage().contains("timeout")) {   // 靠 message 猜类型
        throw new RuntimeException("AI响应超时，请重试");
    }
    throw new RuntimeException("AI服务暂时不可用");
} catch (Exception e) {

}
```

另外 `parseJsonObj` 解析失败返回 `null`，而 `RECOMMEND_CATEGORY` 分支直接 `output.setCategory(category)`，前端拿到的是 `category: null`，只能显示"推荐失败"，日志里也只有一个 warn。

**风险**：抛出时没带 `cause`，排查时看不到根因（到底是 DNS、TLS、429 还是 5xx）；靠 message 匹配判断超时，一旦 JDK 或客户端换了文案就失效，而 `SocketTimeoutException` 本来就是一个类型。

**改法**：自定义异常带 code 与 cause，按类型分类，解析失败走显式降级。

```java
catch (ResourceAccessException e) {
    Throwable root = e.getMostSpecificCause();
    if (root instanceof SocketTimeoutException)
        throw new AiException("AI_TIMEOUT", "AI 响应超时，请重试", e);
    throw new AiException("AI_UNAVAILABLE", "AI 服务暂时不可用", e);
} catch (HttpStatusCodeException e) {   // 401/429/5xx
    throw new AiException("AI_HTTP_" + e.getStatusCode().value(), "AI 服务返回异常", e);
}
```

解析失败时保留原始响应，别只留一句 warn：

```java
log.warn("AI JSON 解析失败，action={}, raw={}", action, abbreviate(raw, 500));
// 返回明确降级结果：category 为空时给出默认分类 + reason="AI 未返回有效分类，请手动选择"
```

**验收**：日志里能看到完整的异常链与 status code；停掉网络调一次 AI，返回的提示是"超时/不可用"而非笼统的"繁忙"。

### P1-6 写操作没有事务边界

**位置**：`service/impl/ArticleServiceImpl.java` 全文；`UserServiceImpl` 同理。

**现状**：所有方法都没标 `@Transactional`。当前每个方法只碰一张表，问题被规模掩盖着。

**风险**：一旦出现"发布文章 + 写审计记录""删除文章 + 清封面图记录"这类组合写，前半段成功后半段失败就会留下脏数据；而这种不一致在测试环境几乎复现不出来。

**改法**：写方法统一加注解，ROLLBACK 范围显式声明。

```java
@Transactional(rollbackFor = Exception.class)
public void add(Article article) { ... }
```

同时补一条约定：事务边界只落在 Service，Controller 不开事务、Mapper 不加事务。

**验收**：人为让多表写入的第二段抛异常，第一段的数据不落库。

### P1-7 用户上下文靠 ThreadLocal 隐式传递

**位置**：`interceptors/LoginInterceptor.java` 第 37 行写入；`ArticleServiceImpl.add/list/update` 第 29、45、61 行读取；`UserController.userInfo/updatePassword` 也读。

**现状**：拦截器把 claims 放进 `ThreadLocal`，Service 与 Controller 各自 `ThreadLocalUtil.get()` 取 `id`。上下文没有出现在任何方法签名里。

**风险**：`ThreadLocal` 只对当前线程有效。一旦 AI 调用改成异步、或者用线程池跑批处理，取到的是别的请求的上下文（甚至 `null`，然后 `map.get("id")` 抛 NPE）。`afterCompletion` 已经做了清理，防住了内存泄漏，但防不住跨线程失效。P0-4 的登录 rehash NPE 就是"在拦截器白名单接口里读 ThreadLocal"的直接例子。

**改法**：优先显式传参——Service 方法多一个 `Integer currentUserId` 参数，调用点从统一的地方取一次。若为了少改代码要保留 `ThreadLocal`，至少在异步任务里传播上下文：

```java
// 用 TaskDecorator 把主线程上下文复制到工作线程
public class ContextCopyingDecorator implements TaskDecorator {
    public Runnable decorate(Runnable r) {
        Map<String, Object> ctx = ThreadLocalUtil.get();
        return () -> {
            ThreadLocalUtil.set(ctx);
            try { r.run(); } finally { ThreadLocalUtil.remove(); }
        };
    }
}
```

**验收**：`ArticleServiceImpl` 的三个方法签名里能看到用户 id；异步执行时不会出现 NPE。

### P1-8 放行白名单硬编码在配置类

**现状**：

```java
registry.addInterceptor(loginInterceptor).excludePathPatterns("/user/login", "/user/register");
```

**验收**：删掉 `excludePathPatterns` 后登录、注册仍可匿名访问；其他接口仍返回 401。

### P1-9 全局异常一把抓，message 直接回显

**位置**：`exception/GlobalExceptionHandler.java` 全文。

**现状**：

```java
@ExceptionHandler(Exception.class)
public Result handleException(Exception e){
    e.printStackTrace();
    return Result.error(StringUtils.hasLength(e.getMessage()) ? e.getMessage() : "操作失败");
}
```

**风险**：三层问题叠在一起。第一，`@ExceptionHandler(Exception.class)` 把参数校验异常、SQL 异常、空指针全收进同一个出口，前端只能看到 `MethodArgumentNotValidException` 的英文技术信息，或者干脆看到一句 SQL 片段。第二，`e.getMessage()` 回显等于把内部细节交给前端。第三，`printStackTrace()` 打到标准错误，没有级别、没有上下文、没有 traceId，线上排查基本靠猜。

**改法**：分类处理，对外友好、对内详细。先补齐三个前置条件，否则下面的片段编译不过、验收也做不到：

1. `Result` 只有 `error(String)`（`Result.java:27`），需要加一个带 code 的重载：

```java
public static Result error(Integer code, String message) {
    return new Result(code, message, null);
}
```

2. `BizException` 目前不存在，需要新建：

```java
public class BizException extends RuntimeException {
    private final int code;
    public BizException(int code, String message) { super(message); this.code = code; }
    public BizException(String message) { this(400, message); }
    public int getCode() { return code; }
}
```

3. 全项目目前没有任何 traceId 基础设施（搜不到 `MDC`），需要补一个 Filter：

```java
@Component
public class TraceIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        MDC.put("traceId", traceId);
        res.setHeader("X-Trace-Id", traceId);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.remove("traceId");
        }
    }
}
```

并在日志 pattern 里输出 `%X{traceId:-}`（`logging.pattern.console` 或 `logback-spring.xml`）。

然后才是异常分类：

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public Result handleValid(MethodArgumentNotValidException e) {
    String msg = e.getBindingResult().getFieldErrors().stream()
            .map(f -> f.getDefaultMessage()).collect(Collectors.joining("；"));
    return Result.error(400, msg);
}

@ExceptionHandler(BizException.class)          // 业务异常，安全回显
public Result handleBiz(BizException e) {
    return Result.error(e.getCode(), e.getMessage());
}

@ExceptionHandler(Exception.class)             // 兜底，不回显
public Result handleOther(Exception e) {
    log.error("未预期异常 traceId={}", MDC.get("traceId"), e);
    return Result.error(500, "系统繁忙，请稍后重试");
}
```

> 注意 `Result.code` 目前是业务码（0 成功、1 失败），前端只判断 `code === 0`。引入 400/403/500 后前端仍按非 0 走失败分支，行为不变；如果希望同时返回 HTTP 状态码，再考虑 `ResponseEntity`，不要混用两套语义。

**验收**：故意传一个不合法的注册参数，前端提示是中文可读句；故意触发空指针，前端只看到"系统繁忙"，日志里能看到完整栈与 traceId。

### P1-10 token 用量硬编码为 0，成本不可观测

### P1-11 JWT 签名密钥硬编码（2026-11-16 新增）

**位置**：`utils/JwtUtil.java` 第 11 行。

**现状**：

```java
private static final String KEY = "itheima";
```

HMAC256 的密钥直接写在源码里，且是教程项目里公开的默认值。

**风险**：拿到源码的人都能签发任意 claims 的 token。当前 Redis 白名单要求 token 本身存在于 Redis（`LoginInterceptor.java:29-33`），伪造的 token 不在白名单里，会被拦住，所以暂不构成直接接管；但这道防线只要以后调整（比如改成只验 JWT、做无状态多实例、加刷新令牌），硬编码密钥立刻变成"任何人可伪造任意用户"。面试里也是明显的减分项。

**改法**：密钥外置，并让应用在缺失时启动失败。

```java
@Component
public class JwtUtil {
    private final Algorithm algorithm;

    public JwtUtil(@Value("${jwt.key}") String key) {
        this.algorithm = Algorithm.HMAC256(key);
    }
    // genToken / parseToken 改为实例方法
}
```

`application.yml` 不写默认值，只写 `jwt.key: ${JWT_KEY}`；密钥至少 32 字节随机串。由于 `JwtUtil` 现在是静态工具类，调用点（`LoginInterceptor`、`UserController`、`JwtTest`）需要改为注入，这是本条的主要改动量。

**验收**：源码中搜不到 `KEY = "itheima"`；用旧密钥签发的 token 被拒绝；未设置 `JWT_KEY` 时应用启动失败并给出明确提示。

### P1-12 会话语义不一致，且没有服务端登出（2026-11-16 新增）

**位置**：`utils/JwtUtil.java` 第 17 行；`controller/UserController.java` 第 99、158-160 行；`src/views/Layout.vue` 第 55 行。

**现状**：

- JWT 自身有效期 12 小时（`JwtUtil.java:17`），Redis 白名单 TTL 只有 1 小时（`UserController.java:99`），实际会话 1 小时就失效，12 小时形同虚设。
- 没有登出接口。前端"退出登录"只是 `tokenStore.removeToken()`（`Layout.vue:55`），服务端 Redis 里的 token 仍然有效，被窃取的 token 在 TTL 内还能继续用。
- 修改密码时只删除当前请求携带的那个 token（`UserController.java:158-160`），其他设备上的旧 token 仍然有效。

**风险**：用户对"登录多久、改密后是否强制下线、退出是否真的退出"没有一致预期；安全事件发生时无法主动失效会话。

**改法**：

1. 统一 TTL：JWT `exp` 与 Redis TTL 用同一份配置（建议 2 小时），或在拦截器里做滑动续期。
2. 增加 `POST /user/logout`，从 `Authorization` 取 token 并 `delete` Redis key；前端退出时先调接口再清本地。
3. 改密后失效该用户全部会话：登录时除 `token -> token` 外，再维护一个 `user:tokens:{userId}` 的 Set，改密时取出集合逐个删除。

```java
// 登录时
operations.set(token, token, ttl, TimeUnit.HOURS);
redisTemplate.opsForSet().add("user:tokens:" + userId, token);
redisTemplate.expire("user:tokens:" + userId, ttl, TimeUnit.HOURS);

// 改密 / 强制下线时
Set<String> tokens = redisTemplate.opsForSet().members("user:tokens:" + userId);
if (tokens != null) tokens.forEach(redisTemplate::delete);
redisTemplate.delete("user:tokens:" + userId);
```

**验收**：退出登录后旧 token 调任意接口返回 401；改密后另一台设备上的 token 返回 401；会话实际时长与配置一致。

### P2-2 javax 与 jakarta 命名空间混用

### P2-3 `request.js` 两处会导致错误被吞或抛 TypeError

**位置**：`src/utils/request.js` 第 20-23 行、第 40 行。

**现状一**：请求拦截器的错误回调没有 `return`：

```js
(err) => {
    Promise.reject(err)      // 少了 return，等价于返回 undefined，错误被静默吞掉
}
```

**现状二**：响应拦截器直接读 `err.response.status`，网络断开、超时、DNS 失败时 `err.response` 是 `undefined`，这里会先抛 `TypeError`，真正的原因反而被掩盖。

**改法**：

```js
(err) => Promise.reject(err),

err => {
    if (!err.response) {
        ElMessage.error('网络异常，请检查网络后重试')
        return Promise.reject(err)
    }
    if (err.response.status === 401) {
        ElMessage.error('请先登录')
        router.push('/login')
    } else {
        ElMessage.error(`服务异常（${err.response.status}）`)
    }
    return Promise.reject(err)
}
```

**验收**：断网后点任意列表页，提示"网络异常"而不是"服务异常"；页面不出现未捕获的 TypeError。

### P2-6 Redis 与数据源配置过于裸奔

### P2-7 上传链路：没有类型校验，且每次新建 OSS 客户端

**位置**：`controller/FileUploadController.java` 第 13-19 行；`utils/AliOssUtil.java` 第 20-37 行；`application.yml` 第 7-10 行。

**现状**：

```java
String originalFilename = file.getOriginalFilename();
String fileName = System.currentTimeMillis() + originalFilename;
String url = AliOssUtil.uploadFile(fileName, file.getInputStream());
```

- 不校验扩展名、Content-Type 或文件头，任何登录用户都能把 `.html`、`.svg`（含脚本）上传到公开的 OSS 桶，返回的 URL 直接挂在你的域名下。
- 对象名直接拼接用户提供的原始文件名，没有长度与字符限制。
- `AliOssUtil.uploadFile` 每次调用都 `new` 一个 `OSSClient` 再 `shutdown()`，和 P1-4 是同一类问题。
- 封面图经后端中转，文件在两跳之间各走一次公网流量，"10MB 限制"是带宽妥协而非产品需求。

**风险**：上传 HTML/SVG 可被用作托管钓鱼页或存储型 XSS 的载荷，且是**公开可访问**的；原文件名还可能带路径分隔符或超长字符；并发上传时反复建连、占 Tomcat 线程与堆内存。

**改法**：

1. 白名单校验扩展名 + `Content-Type` +（最好）文件魔数，只允许 `jpg/jpeg/png/gif/webp`：

```java
private static final Set<String> ALLOWED = Set.of("jpg", "jpeg", "png", "gif", "webp");

String ext = StringUtils.getFilenameExtension(originalFilename);
if (ext == null || !ALLOWED.contains(ext.toLowerCase())) {
    throw new BizException("仅支持 jpg/jpeg/png/gif/webp 图片");
}
if (file.getContentType() == null || !file.getContentType().startsWith("image/")) {
    throw new BizException("文件类型不合法");
}
String objectName = UUID.randomUUID() + "." + ext.toLowerCase();
```

2. `AliOssUtil` 改成单例 Bean，构造时创建 `OSSClient`，`@PreDestroy` 时关闭。
3. 如果桶不需要公开读，改成私有桶 + 短期签名 URL。
4. STS 临时凭证 + 前端直传属于可选进阶：能省带宽，但对当前规模是额外复杂度，时间紧可以不做；**类型校验必须做**。

**验收**：上传 `.html`/`.svg` 被拒绝；连续上传 10 次只复用一个 OSS 客户端；上传后的内容不是任意 HTML。

### P2-8 前端 AI 请求没有超时与取消

**位置**：`src/utils/request.js` 第 8 行 `axios.create({baseURL})`。

**现状**：实例只配了 `baseURL`，没有 `timeout`。后端 AI 的读超时是 30 秒，前端会一直转圈到后端返回为止；用户中途切换文章或关闭编辑器，在途请求也不会被取消，回来还可能把结果写进另一篇文章。

**改法**：前端超时必须**不短于**后端读超时，否则后端还在正常处理，前端先报超时。

```js
// 后端 ai.api.read-timeout 默认 30000，前端留 5 秒余量
const instance = axios.create({ baseURL, timeout: 35000 })
```

```js
// AI 面板里保存 controller，切换文章/卸载时 abort
const controller = new AbortController()
await generateAi({ ...payload }, { signal: controller.signal })
onBeforeUnmount(() => controller.abort())
```

`package.json` 里 axios 是 `^1.5.1`，支持 `signal`，不需要额外改造。

**验收**：切走再切回不出现"旧结果串进新文章"；后端挂起时 35 秒左右给出超时提示，而不是 20 秒就误报。

### P2-9 令牌存在 localStorage，XSS 一次即失守

**位置**：`src/stores/token.js`（pinia + `pinia-persistedstate-plugin`）。

**现状**：令牌被持久化到 `localStorage`，任一脚本都能读。

**风险**：与 P2-4 叠加就是完整的攻击链——AI 返回的恶意 HTML 执行后，直接把 token 取走，账号即被接管。单个问题都不致命，串起来就致命。

**改法**：改为 HttpOnly + SameSite=Lax 的 Cookie 承载令牌，前端不再持有；开发期已经有 Vite 代理（`/api` → `localhost:8080`），同源，Cookie 方案不需要额外改造跨域。

需要提前说明的是，这条**工作量比"交付观感"级别大**：后端要改成从 Cookie 读取、补登出清除、评估 CSRF、调整接口测试；如果时间有限，优先做 P2-4 的净化来切断攻击链，Cookie 迁移列为可选进阶。

**验收**：`localStorage` 里搜不到 token；F12 的 `document.cookie` 里也读不到。

### P2-10 README 还是 Vite 模板原文

**位置**：`README.md`。

**现状**：全文是 "This template should help get you started developing with Vue 3 in Vite"，没有一句说这个项目是什么、怎么跑起来。

**风险**：面试官点开仓库第一屏就是这个模板说明，等于告诉对方"我没打理过这个项目"。这是性价比最高的一处改动：十分钟，观感差别很大。

**改法**：至少写四段——项目简介与截图、技术栈、启动步骤（建库 → 起 Redis → 设 `DB_PWD`/`DEEPSEEK_API_KEY` → 后端起 8080 → 前端 `npm run dev`）、接口清单或功能列表。

**验收**：换一台机器按 README 能跑起来，不需要问作者。

### P2-11 AI 接口没有频控与配额（2026-11-16 新增）

**位置**：`controller/AiController.java` 第 18-21 行。

**现状**：只要登录，就能无限次调用 `/ai/writing/generate`。系统里没有任何按用户或全局的调用次数限制，也没有熔断。

**风险**：AI 接口直接消耗 DeepSeek 的付费额度，一个脚本循环或前端误触就能把额度刷光；P1-10 只解决"看得见成本"，不解决"防得住"。多用户场景下也无法区分是谁在滥用。

**改法**：用 Redis 做一个最低成本的按用户每日/每小时计数，超限返回 429；再加一个全局日上限兜底。

```java
String key = "ai:rate:" + userId + ":" + LocalDate.now();
Long count = redisTemplate.opsForValue().increment(key);
if (count != null && count == 1L) {
    redisTemplate.expire(key, Duration.ofDays(1));
}
if (count != null && count > 50) {
    throw new BizException(429, "今日 AI 调用次数已达上限，请明天再试");
}
```

计数放在 `AiServiceImpl.generate` 入口或独立的 `RateLimitService`，便于测试；阈值写进配置而不是硬编码。

**验收**：同一用户第 51 次调用返回 429 与中文提示；另一个用户不受影响；跨天后自动恢复。

### P2-12 改密接口的口令规则与注册不一致（2026-11-16 新增）

**位置**：`controller/UserController.java` 第 64 行（注册）与第 134-157 行（改密）。

**现状**：注册和登录用 `@Pattern(regexp = "^\\S{5,16}$")` 限制口令，改密接口只检查了非空（`StringUtils.hasLength`），既没有长度/字符约束，也没有"新口令不能与旧口令相同"的校验。参数还是裸的 `Map<String,String>`。

**风险**：用户可以绕过注册规则把口令改成 1 位；改密接口也无法被 Bean Validation 统一校验，后续加规则容易漏。

**改法**：改密请求改为 DTO，字段上加与注册一致的 `@Pattern`；`new_pwd` 与 `old_pwd` 相同时直接拒绝。校验逻辑随 P1-1 一起下沉到 `LoginService.changePassword`。

```java
@Data
public class UpdatePasswordDTO {
    @NotBlank(message = "原密码不能为空")
    @JsonProperty("old_pwd")          // 前端现有字段名是下划线风格
    private String oldPwd;

    @Pattern(regexp = "^\\S{5,16}$", message = "新密码长度为5-16位，不能包含空格")
    @JsonProperty("new_pwd")
    private String newPwd;

    @NotBlank(message = "确认密码不能为空")
    @JsonProperty("re_pwd")
    private String rePwd;
}
```

**验收**：新口令为 `1` 时返回中文校验提示；新旧口令相同被拒绝；两次输入不一致仍返回原提示。

## 不建议做的事

下面这几件事看起来"更像大厂项目"，但对这个规模是负担，做了反而要在面试里多解释一层：

- **不要拆微服务、不要上注册中心与网关**。当前只有 5 个 Controller、3 张表、单机部署，拆开之后要么靠本地多进程硬凑，要么引入一堆运维成本，性能收益为零。
- **不要引入 MQ、Elasticsearch、Kafka**。没有真实的数据量与并发场景，面试官第一个问题就是"QPS 多少、为什么需要它"，答不上来比不做更糟。
- **不要为了分层而分层**。给 3 张表建 DDD 聚合根、给 5 个 Controller 建抽象工厂，是典型的过度设计。
- **不要一次全改**。P1 的重构彼此有关联（VO 拆分会影响策略化后的返回值），按批次推进，每批跑通再动下一批。
- **P2-7 的 STS 直传、P2-9 的 Cookie 迁移属于可选进阶**，时间紧可以跳过；先用上传类型白名单和 DOMPurify 把风险切断。

## 改完之后，简历上能讲的四个点

按价值排序，这四项改动能支撑起面试里的技术对话，而不只是功能罗列：

1. **越权治理（P0-1、P0-3、P0-5）**：文章、用户资料、分类三条链路都从"只按请求体 id 操作"改为"SQL 条件 + Service 归属校验 / 入参 DTO 收窄"，能讲清 IDOR 与 mass assignment 的成因，以及为什么单靠前端传参不可信。
2. **口令存储演进（P0-2、P0-4）**：MD5 → BCrypt，且处理了存量数据兼容、登录时静默 rehash、双重加密与拦截器白名单导致的上下文缺失，这一段有真实的迁移设计，不是换个 API。
3. **AI 模块策略化（P1-3）**：三处重复分派收敛为一个 `AiActionHandler` 契约，新增动作零改动已有代码，能讲清"为什么 switch 会随动作数量线性腐化"。
4. **外部调用与会话治理（P1-4、P1-5、P1-6、P1-12）**：连接池复用、异常分类与降级、事务边界、JWT 有效期与 Redis 白名单的一致性，能把"同步调 30 秒的外部接口会怎样拖垮 Tomcat""退出登录为什么需要服务端参与"讲成具体的故事。

每一项都要能回答"改之前是什么样、为什么那样不行、改之后怎么验证"，这比在简历上多写两行技术栈有用得多。
